## 1. 文档目标

本文档用于把《销售规范流程制度（试行）》与《销售提成方案制度（试行）》中的真实职责，转换为一套可执行的“全流程人工测试账号矩阵”。

本文档重点回答以下问题：

- 全流程人工测试至少应拆出哪些自然人账号
- 这些账号分别挂在哪些组织下更符合制度语义
- 制度角色、审批角色和系统账号应如何对应
- 当前实现仍较粗粒度时，测试账号应如何临时映射到现有权限 key

本文档不是最终平台角色配置表，也不是数据库 seed 脚本本身；它是后续 seed 重整、权限收敛和人工验收编排的参考输入。

---

## 2. 当前边界

本轮文档收口只覆盖：

- 全流程人工测试所需的账号、组织和角色拆分
- 当前权限模型下的临时授权映射建议
- 当前实现与制度职责之间的已知不一致点

本轮文档不直接覆盖：

- 新权限 key 设计
- 新组织树 DDL 或平台治理表结构调整
- 审批规则引擎重构
- 开发环境真实密码或最终 seed 明细

---

## 3. 收口原则

1. 制度职责优先于当前 seed 便利性
   - `admin` 只适合作为 smoke 或系统兜底账号，不应继续充当全流程验收主账号。
2. 平台角色、业务职责角色、审批角色分层表达
   - 同一个自然人可以兼任多类角色，但人工测试应尽量拆成独立账号，避免职责串味。
3. 全流程人工测试优先验证职责边界
   - 需要验证“谁发起、谁确认、谁审批、谁登记、谁复核”，而不是只验证接口能否成功。
4. 当前权限较粗时允许临时并权
   - `project:write`、`contract:finance:manage`、`commission:*` 当前粒度仍偏粗；在实现未细化前，测试账号可做临时并权，但要显式记录这不是长期目标。

---

## 4. 当前最小实现现状

当前开发 seed 已按第 7 节的账号矩阵补齐首批全流程人工测试账号，并保留 `admin` / `viewer` 作为最小 smoke 入口。

当前已知限制至少包括：

- 合同审核类审批当前默认归属 `vp_owner`，提成发放 / 调整审批当前默认归属 `finance_mgr`
- `project:write` 同时覆盖项目推进、合同流转、移交相关写动作，无法准确表达职责边界
- `contract:finance:manage` 同时覆盖财务事实维护和部分经营相关入口
- 提成操作入口当前仍偏向组合权限，细粒度职责拆分尚未完全落地

因此，下面的矩阵现在既是“目标测试租户”，也是当前开发 / 测试 seed 的实现基线；剩余问题主要集中在权限粒度和职责隔离，而不再是账号缺位。

## 5. 制度原生角色与实施派生角色

### 5.1 制度原生角色

| 角色口径              | 来源                                | 说明                                                       |
| --------------------- | ----------------------------------- | ---------------------------------------------------------- |
| 销售人员              | 销售规范流程制度                    | 项目第一责任人，负责线索、立项、报价、签约推进与回款跟踪   |
| 销售负责人            | 销售提成方案制度 / 授权矩阵         | 高一级销售责任角色，负责投标决策、高层介入等关键发起或放行 |
| 技术支持 / 售前       | 销售规范流程制度                    | 负责技术可行性、范围确认、风险判断                         |
| 商务行政              | 销售规范流程制度                    | 负责合同资料、流程文件、移交组织与记录完整性               |
| 商务负责人            | 授权矩阵 / 角色目录                 | 负责商务结果确认、投标结果确认等补充商务判断               |
| 财务人员              | 销售规范流程制度 / 销售提成方案制度 | 负责回款、付款、税务风险、提成计算和发放登记               |
| 副总经理 / 流程负责人 | 销售规范流程制度                    | 负责立项、毛利评审、流程合规放行                           |
| 公司高层              | 销售规范流程制度                    | 负责战略项目、重大例外和高层介入裁量                       |
| 项目负责人            | 角色目录 / 授权矩阵                 | 负责项目移交、执行承接与验收责任                           |

### 5.2 实施派生角色

| 角色口径                  | 来源                | 说明                                               |
| ------------------------- | ------------------- | -------------------------------------------------- |
| 平台管理员                | 平台治理设计        | 负责用户、角色、组织、导航治理，不参与日常业务审批 |
| 销售助理 / 业务登记角色   | 授权矩阵            | 负责到账等业务事实录入                             |
| 制度维护角色              | 角色目录 / 授权矩阵 | 负责提成规则版本维护                               |
| 财务负责人 / 预算审批角色 | 授权矩阵            | 负责提成档位审批、冲销、异常调整等高敏放行         |
| 审计 / 只读观察           | 人工测试需要        | 用于全流程只读验收和职责边界校验                   |

### 5.3 非账号型制度角色

以下口径在第一轮人工测试中不强制要求独立系统账号：

| 角色口径       | 说明                                                       |
| -------------- | ---------------------------------------------------------- |
| 公司管理保留   | 更接近提成分配中的保留权重口径，不一定对应一个固定登录账号 |
| 战略关系推动人 | 可由公司高层账号承接；若后续需要区分外部关系人，再单独拆分 |

## 8. 最小可执行测试分层

### 8.1 最小 smoke 账号

仅做环境探活时，可继续保留：

- `admin`
- `viewer`

这组账号的目标是“系统能否启动、主路径是否还能跑通”，不是“制度职责是否合理”。

### 8.2 全流程人工验收最小账号集

若只追求第一轮全流程人工验收，至少建议具备以下账号：

- `sales_rep`
- `presales`
- `biz_admin`
- `vp_owner`
- `project_mgr`
- `finance_ops`
- `finance_mgr`
- `auditor`

### 8.3 完整制度对照账号集

若需要同时验证职责边界、审批边界和制度角色完整性，建议使用第 7 节的完整矩阵，不再复用万能账号。

## 9. 当前实现兼容性与阻断项

### 9.1 当前兼容性判断

当前实现已经可以使用独立账号完成第一轮全流程人工测试，但仍是“制度角色已拆分、权限边界仍偏粗”的过渡态。

### 9.2 已知阻断项

1. `project:write` 粒度过粗
   - 销售、售前、商务、项目负责人、副总经理当前都可能需要复用这一权限。
2. `contract:finance:manage` 粒度过粗
   - 销售助理、商务行政、财务人员当前难以严格拆开到账登记、财务确认与经营相关入口。
3. 提成入口权限仍偏组合化
   - 若从当前管理端完整走通提成操作入口，财务与制度维护角色可能需要临时并权。

### 9.3 后续落地建议

1. 继续按业务对象动作矩阵细化 `project:*`、`contract:*`、`commission:*` 权限
2. 收口前端路由守卫与后端 guard 的职责边界
3. 把“默认审批人”从开发固定映射推进到可配置或按业务事实派发
4. 在后续制度收口时，再把当前临时并权账号拆回更严格的职责集

---

## 10. 使用约定

- 评审“账号是否合理”时，以本矩阵和制度文档为准，不再以当前 `admin` / `viewer` 的便利性为准
- 设计“谁来测试哪个流程”时，优先看业务职责角色和审批 / 确认角色，再回看当前实现需要的临时权限
- 后续若 seed、审批分派或权限模型发生收口，应优先回写本文件，再同步到具体实现
