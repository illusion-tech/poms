## 1. 文档目标

本文档不是某个专题的补丁说明，而是 `POMS` 当前正式启用的设计到实现治理入口。

它重点回答六个问题：

- 设计在什么条件下才允许进入实现
- 哪些文档可以作为实现输入，哪些只能作为讨论背景
- 一个工程切片在开工、提测、合并、标记完成前分别需要过哪些闸口
- 当实现只覆盖大任务的一部分时，应该如何命名、评审与回写
- 当设计、契约、DDL、实体、测试出现漂移时，应如何阻断和归类
- 谁对“可以开始做”“可以合并”“可以标记完成”分别负责

## 2. 适用原则

### 2.1 单一可信输入原则

同一工程切片在任一时点必须有一组明确的正式输入，不允许实现者自行从多份文档中拼接“我理解的版本”。

当前统一要求：

1. 业务语义以业务主文档为准。
2. 命令边界以 `interface-command-design.md` 为准。
3. DTO / OpenAPI 边界以 `interface-openapi-dto-design.md` 为准。
4. 读侧边界以 `query-view-boundary-design.md` 为准。
5. 持久化冻结边界以 `data-model-prerequisites.md`、`table-structure-freeze-design.md`、`schema-ddl-design.md` 为准。
6. 若这些文档之间尚未收口，则该切片默认不满足开工条件。

### 2.2 先冻结，再编码

评审通过不等于可以开工。

只有当切片已经形成“可直接编码”的冻结输入后，才允许进入实现。

### 2.3 先切片，再交付

若目标过大，必须先拆成可独立完成、可独立验证、可独立回写的子切片。

不允许把“部分实现”挂在“完整任务”名义下合并。

### 2.4 先对齐，再合并

实现是否“基本可跑”不能替代一致性判断。

若设计、契约、DDL、实体、接口、测试之间存在关键漂移，默认阻断合并。

### 2.5 例外必须显式留痕

任何例外放行都必须留下：

- 放行原因
- 风险范围
- 临时接受边界
- 后续清理责任人与时间点

不允许“先合了再说”“后面顺手改”这类隐性例外。

## 3. 正式状态模型

本文件遵循 `ADR-014` 已接受的设计-执行状态模型。

当前正式状态仍以 [README.md](./README.md) 和 [phase2-development-execution-tracker.md](./phase2-development-execution-tracker.md) 的状态定义为准。

本文件负责定义 gate 的使用方式，不新增独立于 `ADR-014` 的状态集合。

### 3.1 文档状态

正式文档状态为：

- `Draft`：默认不可直接作为“已冻结实现输入”；若要启动实现，必须通过例外流程放行。
- `Review`：说明文档已经进入审阅或收口阶段，但仍不自动等于可开工；只有在 `G1 = Pass` 后，相关切片才算具备已冻结实现输入。
- `Accepted`：可作为当前阶段正式设计依据，但切片仍需形成实施基线包，不能跳过 `G1`。
- `Active`：用于治理文档、状态文档和持续维护文档；它们可以作为控制输入，但不能单独替代具体业务切片的冻结输入。
- `Archived`：不得作为当前默认实现输入。

补充说明：

- `Draft (Baseline)`、`Ready for Review` 不再作为独立正式状态。
- `Frozen for Build` 是 `G1 = Pass` 的展示语义，不是新的文档状态。
- `G1 = Pass` 应记录在实施基线包中，并在追踪板 `备注 / 阻塞` 中留下最短必要说明。

### 3.2 任务状态

正式任务状态为：

- `Todo`
- `Doing`
- `Blocked`
- `Done`

### 3.3 Gate 状态

正式 gate 状态为：

- `Pending`
- `Pass`
- `Block`
- `Waived`

当前记录方式统一为：

1. `G1 = Pass`：任务仍可保持 `Todo` 或转入 `Doing`，但需在实施基线包中记录 gate 结论，并在追踪板备注说明通过日期。
2. `G3 = Pass`：通过 PR checklist、评审结论或追踪板备注记录，不额外新增追踪板状态。
3. `G4 = Pass`：才允许把任务标记为 `Done`。
4. 若开工后发现高影响未决设计或关键漂移，任务状态应转回 `Blocked`，而不是继续“带病实现”。

## 4. 统一治理闸口

当前建议把工程推进固定为 5 个闸口。

### G0 立项闸口

目标：确认是否真的需要开一个新切片。

必须回答：

1. 这次变更属于哪个主线 / 任务 / 子任务。
2. 它的最小可交付边界是什么。
3. 它是否跨多个主边界；若跨，是否已拆分。
4. 它是否涉及命令、查询、持久化、权限、审批、敏感数据、前端主路径中的一类或多类。

通过标准：

- 已形成明确切片名
- 已指定主 owner
- 已指明直接输入文档
- 已说明本次明确不做的范围

若未通过：

- 不允许直接开始写 migration、entity、controller 或页面代码。

### G1 冻结闸口

目标：确认切片已具备可直接编码的正式输入。

必须具备一份“实施基线包”。

实施基线包最小内容如下：

1. 切片名称与范围说明
2. 正式输入文档列表
3. 本次权威 SSOT 对照
4. 命令边界
5. DTO / 契约边界
6. 读侧边界
7. 持久化范围
8. guard / 权限 / 审批 / 敏感性边界
9. 测试要求
10. 本次不做的内容
11. 已知风险与例外

通过标准：

- 不存在会直接影响实现边界的未决设计问题
- 数据模型、命令、DTO、query、DDL 至少达到“可编码”状态
- 若为部分交付，已明确标注为子切片，而不是父任务完整交付

若未通过：

- 切片只能停留在 `Todo`
- 若需推进，必须先回写设计文档或新增 ADR

### G2 开工闸口

目标：确认实现者不是“边做边猜”。

开工前必须完成：

1. 阅读实施基线包
2. 确认当前正式输入与历史归档文档的边界
3. 若涉及持久化结构，先写 migration 设计，再写 entity / mapping
4. 若涉及接口契约，先固定 DTO 命名与字段语义，再写 controller / service
5. 若涉及高敏或审批，先固定 guard / 审批摘要链，再做业务逻辑

通过标准：

- 实现者能明确说出本次 SSOT
- 关键命名已冻结，不再边做边改
- 本次测试层级已确定

### G3 合并闸口

目标：确认本次 PR 没有把漂移带入主干。

G3 采用“通用必填 + 按切片类型追加”的风险分层方式。

#### G3.1 通用必填

所有切片都必须附带：

1. 本次切片类型与范围说明
2. 实施基线包或正式输入链接
3. 本次明确不做范围
4. 测试覆盖清单与未覆盖项说明
5. 例外项与已知风险说明（如无则写无）

#### G3.2 按切片类型追加

1. `docs-only` / `process-only`
   - 只需补“影响范围说明 + 无行为变更声明 + 需要联动更新的入口文档清单”
2. `refactor-only`
   - 补“外部行为不变说明 + 关键回归验证方式”
3. `query-only` / `frontend-only`
   - 补“query / view 边界对照表”或“页面 / 客户端行为对照表”
   - 若涉及前端主路径、序列化、鉴权、OpenAPI client 或关键交互，还应说明是否触发 E2E 要求
4. `api/command`
   - 补“route 到 command 设计对照表”
   - 补“contract / DTO 到 controller 输入输出对照表”
5. `persistence`
   - 补“migration 到 entity 对照表”
   - 补“migration / DDL / entity 一致性检查结果”
   - 补“drift 归类结论”
6. `cross-layer-high-risk`
   - 同时满足以上相关类型要求
   - 如涉及前后端主路径或审批、权限、结算、状态流转等关键能力，还应显式说明 E2E 是否已补或为何不补

#### G3.3 持久化切片追加要求

若切片涉及持久化结构，还必须给出：

1. migration SQL 已手写
2. migration 与 ORM metadata 已完成一致性检查
3. 若存在 drift，已明确归类为真实遗漏、可接受差异或工具噪声

#### G3.4 默认阻断条件

阻断条件包括：

- 大任务名义下只交付了部分能力，但未拆成子切片
- 契约命名与实体命名明显漂移
- migration / entity / DDL 三者存在关键不一致
- 文档说有的命令或查询，在代码里没有最小闭环
- 测试只覆盖 happy path，没有覆盖关键失败路径
- 本次切片类型明显较轻，却提交了不匹配的大量空模板，导致证据失真

### G4 完成闸口

目标：确认“Done”代表可以被后续切片依赖。

进入 `Done` 前必须全部满足：

1. 代码已合并
2. 文档已回写
3. 执行追踪板已更新
4. 测试已完成并记录范围
5. 若涉及持久化结构，已完成 SQL-first 一致性判断
6. 若存在未完成范围，父任务未被错误关闭

补充约束：

- 子切片 `Done` 不等于父任务 `Done`
- 存在显著例外时，不得标记 `Done`，最多保持 `Doing` 或转为 `Blocked`

## 6. 大任务与子切片治理

为避免“大任务名义下合入部分实现”，当前建议固定以下规则。

### 6.1 何时必须拆子切片

出现以下任一情况时，必须拆分：

1. 同时跨命令、查询、持久化、前端主路径且无法在一次评审中稳定收口。
2. 同一任务下存在多个可独立验收的来源类型或对象链。
3. 某一部分已冻结，另一部分仍在评估。
4. 部分能力能先交付，但其余能力短期内不会跟上。

### 6.2 子切片命名要求

子切片名称应直接体现边界，不允许使用模糊命名。

推荐示例：

- `EX-06A rate-version-and-labor-record`
- `EX-06B non-labor-source-mapping`
- `EX-06C cost-record-query-and-traceability`

不推荐：

- `EX-06 fix`
- `EX-06 first pass`
- `EX-06 partial`

### 6.3 部分交付规则

若 PR 只覆盖部分能力，必须同时满足：

1. 标题或说明明确写出“本次只覆盖哪些子边界”。
2. 文档回写中明确“哪些能力尚未实现”。
3. 父任务保持未完成状态。
4. 下游实现不得假设父任务已经整体可用。

## 7. 评审角色与责任

当前建议把评审责任拆成三类，而不是由单个 reviewer 隐式兜底。

### 7.1 设计 owner

负责：

- 确认本切片的正式输入
- 处理未决设计问题
- 批准是否达到 `G1 = Pass`

不负责：

- 替实现者补 migration / entity / test 对照表

### 7.2 实现 owner

负责：

- 按实施基线包编码
- 提交对照材料
- 标明本次留白、例外与已知风险

不允许：

- 自行改变正式输入却不回写文档
- 在父任务名义下交付子范围

### 7.3 合并 reviewer

负责：

- 审查实现是否遵守正式输入
- 审查对照材料是否完整
- 审查是否满足合并闸口

不应承担：

- 替作者重新做设计收口
- 在关键漂移存在时以“先 merge 后补文档”方式放行

### 7.4 当前控制 owner

当前控制 owner 指维护当前正式实施入口的负责人，通常对应：

- `phase2-mainline-delivery-plan.md`
- `phase2-lx-t04-full-mainline-development-decision.md`
- `implementation-delivery-guide.md`
- `phase2-development-execution-tracker.md`

当前控制 owner 负责：

- 判定新治理是否适用于某个切片
- 在设计 owner 与 merge reviewer 意见冲突时拍板
- 批准重大例外、过渡豁免与 grandfathering
- 决定何时把试运行规则升级为强制门禁

不负责：

- 替实现者准备证据材料
- 替设计 owner 收口具体业务规则

## 8. 一致性检查清单

### 8.1 文档到代码一致性

至少检查：

1. 对象名是否一致
2. 字段名是否一致
3. 状态名是否一致
4. route 命名是否一致
5. 请求 / 响应字段是否一致
6. 本次明确不做的内容是否真的未被误写成“已完成”

### 8.2 持久化一致性

至少检查：

1. migration 与 `schema-ddl-design.md` 是否一致
2. migration 与 entity 是否一致
3. 外键、唯一约束、索引、空值策略是否一致
4. ORM 无法表达的数据库特性是否已单独记录

### 8.3 契约一致性

至少检查：

1. shared contract / API contract 与 controller 实际输入输出是否一致
2. 日期、时间、标识符、金额等类型是否一致
3. 对外命名与对内命名是否存在未解释的双轨

### 8.4 测试一致性

至少检查：

1. 关键成功路径是否覆盖
2. 关键失败路径是否覆盖
3. 关键一致性风险是否覆盖
4. 若未补 E2E，是否已说明理由

## 9. 例外治理

现实中允许例外，但不允许无记录例外。

### 9.1 可接受例外的类型

仅建议接受以下几类：

1. 工具能力差异
2. 仓库历史遗留 drift
3. 临时外部依赖阻塞
4. 已明确拆出的后续子切片留白

### 9.2 例外等级与授权链

为避免口头放行，当前建议把例外分成三类。

#### E1 轻量例外

典型场景：

- `docs-only` / `refactor-only` 切片不需要提交重型对照表
- 低风险切片的某项证据可由更轻量说明替代

批准要求：

- 实现 owner
- merge reviewer

放行边界：

- 可进入 `G3`
- 若不影响下游可信输入，可进入 `G4 / Done`

#### E2 中等级例外

典型场景：

- 已开工旧切片在过渡期内补不齐完整 `G0 / G1` 包
- 受临时外部依赖影响，某项验证需延期
- 某一项正式输入仍在收口，但当前切片只消费已冻结子边界

批准要求：

- 设计 owner
- merge reviewer

放行边界：

- 可进入 `G3`
- 是否允许进入 `G4 / Done`，取决于该例外是否影响下游切片把本切片作为可信输入继续依赖
- 若会影响下游可信输入，最多停留在 `Doing` 或 `Blocked`

#### E3 重大例外

典型场景：

- 未通过 `G1` 就要进入实现
- 持久化 / 契约 / DDL 关键漂移仍未解决
- 需要在存在重大已知风险的情况下合并关键主路径代码

批准要求：

- 设计 owner
- merge reviewer
- 当前控制 owner

放行边界：

- 可在极少数情况下进入临时合并或试验分支
- 默认不允许进入 `G4 / Done`
- 若设计 owner 与 merge reviewer 意见冲突，由当前控制 owner 拍板

### 9.3 不可接受的例外

以下情况默认不应放行：

1. 关键字段命名漂移但未回写
2. migration / entity / contract 关键语义不一致
3. 实现范围显著小于任务定义却未拆任务
4. 用单测通过替代真实契约或持久化一致性判断
5. 设计仍在评估中但代码已按“最终基线”合并

### 9.4 例外超期处理

若例外已设置 `Cleanup Due` 且到期仍未清理，默认执行以下规则：

1. 该例外不再视为自动有效，必须重新审批。
2. 依赖该例外的后续切片不得按“问题已接受”继续推进。
3. 若该例外影响当前切片的可信输入地位，则当前切片不得新标记为 `Done`。
4. 若该切片已处于 `Done`，则应新增后续治理任务或清基线任务，而不是无声遗忘。

### 9.5 例外记录模板

```md
- Exception ID:
- Slice:
- Trigger:
- Accepted By:
- Scope:
- Risk:
- Temporary Boundary:
- Cleanup Owner:
- Cleanup Due:
```

## 10. 生效范围与过渡办法

### 10.1 生效日期

本文件自 2026-04-11 起按 `ADR-014` 的正式状态模型生效。

### 10.2 默认适用范围

以下切片默认必须遵守本文件：

1. 2026-04-11 之后新建的切片
2. 2026-04-11 之后发生范围重定义、子切片拆分或大幅扩边的既有切片
3. 2026-04-11 之后首次进入合并评审、且涉及 command / DTO / query / persistence / guard 关键边界的切片

### 10.3 grandfathering 规则

对本文件生效前已经 `Doing` 的切片，当前采用有限 grandfathering：

1. 不要求追溯性补齐完整历史 `G0` 材料。
2. 若后续只做局部收尾，可按当前范围继续推进，但在进入下一次关键合并前，至少要补最小实施基线包、风险说明和相应 `G3` 证据。
3. 若该旧切片在生效后继续扩边、增新对象链、增新持久化结构或增新命令主路径，则应视为重新纳入本治理。
4. grandfathering 的适用与否，由设计 owner 和当前控制 owner 共同确认；若存在分歧，由当前控制 owner 拍板。

### 10.4 与当前追踪板的衔接

当前统一采用以下最小衔接规则：

1. 不新增 `ADR-014` 之外的追踪板状态值。
2. `G1`、`G3`、例外与 grandfathering 结果，统一记录在实施基线包、PR checklist 和追踪板备注中。
3. 任务只有在满足 `G4` 时才能标记为 `Done`。

## 11. 建议接入 CI / PR Checklist 的门禁项

当前建议至少逐步接入以下门禁。

### 11.1 立即可执行的 PR checklist

1. 已附实施基线包链接
2. 已附文档到代码对照表
3. 已附 migration / entity / contract 对照表
4. 已说明本次明确不做范围
5. 已说明测试覆盖与未覆盖项

### 11.2 中期建议自动化

1. `migration-check`
2. OpenAPI / contract 生成与 diff 校验
3. 命名一致性 lint
4. 关键 schema smoke test
5. 追踪板状态与 PR 标签一致性检查

## 12. 常见反模式

以下行为应视为治理反模式：

1. 把 `Review` 当作“可以直接写代码”。
2. 在没有实施基线包的情况下直接开工。
3. 一边实现一边修改字段命名，但不回写文档。
4. 只做了一部分能力，却继续使用父任务标题。
5. 以“后面再统一收口”为由合入关键漂移。
6. 用“单测通过”替代“契约、DDL、实体一致”。
7. 先合并代码，再补 tracker、文档和例外说明。

## 13. 推荐落地顺序

若要把本文件真正落地，当前建议按以下顺序推进：

1. 从 2026-04-11 之后的新切片开始强制执行 `G0 / G1 / G3 / G4`。
2. 对生效前已开工切片，按 grandfathering 规则逐步纳入，不做一刀切追溯。
3. 为每个新切片强制补“实施基线包”。
4. 在 PR 模板中加入风险分层后的最小对照清单。
5. 将 `migration-check`、契约 diff 等逐步升级为 CI 门禁。
6. 等流程稳定后，再决定是否把 gate 结果结构化进追踪板字段，而不是先引入双轨状态。

## 14. 当前结论

`POMS` 后续若要减少“设计已评审但未冻结就进入实现”“实现范围与任务定义不一致”“契约、DDL、实体与测试多层漂移”这类问题，关键不在增加更多文档，而在于：

1. 明确单一正式输入
2. 增加冻结闸口
3. 强制子切片治理
4. 在合并前提交一致性对照材料
5. 把例外从隐性默许改为显式留痕

本文件的价值不在“让流程更重”，而在于把原本靠经验判断的隐性规则，变成可复核、可执行、可追责的显性闸口。
