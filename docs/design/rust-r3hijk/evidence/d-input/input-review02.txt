3.2 列表解析与跨转换（service:28-35,85-111,196-250）
按 customer → lead → project 顺序逐项 require，缺项抛原对象类型和原输入 id 的 NotFoundException。
customer 只加 customer 自身目标；不会把该客户全部 Lead/Project 讨论自动聚合。
lead 只加该 Lead；project 加该 Project，若 sourceLeadId 真值，再 findLeadById，存在才加来源 Lead。
来源 Lead 不存在时跳过，不能新增 404。Project target 的 leadId 始终 null；sourceLeadId 不写进 thread。
多目标 customerId 去掉空值后若多于一个，400 'Discussion query anchors must belong to the same customer'。
同客户的无关 lead/project 允许；不强制它们互为转换关系；uniqueTargets 按 type:id 去重。
历史 Lead 讨论留在原 Lead thread；Project GET 聚合，POST 新讨论仍写 Project thread。
转项目不复制、不迁移、不改历史 thread 或 comment 归属。

3.3 关联校验（service:37-83,129-194）
target 解析成功后 Promise.all 并行 require 三种关联，随后才查/建 thread；多处同时失败的先抛
边界可能依赖完成时序，固定验收一次只引入一个非法关联，不编造多失败固定优先级。
contact：按 id 查，不筛 active/status。不存在 404 CustomerContact；只有 target.customerId 为真值
时检查 contact.customerId 相等。Project.customerId=null 时原代码不限制联系人客户。
competitor/follow-up：按 id 查，不筛状态，不拒绝 voided/superseded follow-up。
顺序：target.customerId 真值且不等则 customer 400；target.projectId 与 record.projectId 均真值
且不等则 project 400；target.leadId 与 record.leadId 均真值且不等则 lead 400。
record 某机会锚点 null 时不拒绝；Customer target 的 lead/project 均 null，不限制同客户其他机会。
Project target 的 leadId=null，不能补 sourceLeadId 校验；Lead target 的 projectId=null，同理。
这些是现有容许行为，Rust 不以“更严谨”为理由收紧。

3.4 thread 持久化、快照与映射（service:44-82,252-296；repo:53-117；entity:13-98）
唯一键 targetObjectType+targetObjectId。一条目标一个 thread；首次新建 thread+comment 一起 flush，
已有 thread 只保存 comment。无源码 upsert、重试、显式目标锁或冲突恢复，不自行发明。
thread 的 targetTitle/customerId/leadId/projectId 是首次建 thread 的快照；后续目标改名不刷新旧 thread。
thread/comment 各 randomUUID，createdAt 由 ORM onCreate(new Date) / DB default 支持；createdBy 来自 session sub。
平台用户不存在时 createdByName=null；联系人读不到时 relatedContactName=null；不抹掉原 relatedContactId。
thread 读不到才抛 BusinessDiscussionThread {threadId} not found。
FK：thread 锚点 restrict；comment thread restrict；三种关联 on delete set null；createdBy 无用户 FK。
新 thread 唯一冲突/关联在校验后被删等 DB 错误保留 Native 原始失败行为，不能先假设 409/400。
同一新建请求返回体的孤 UTF-16 单元与 DB 再读后的值可能不同，需要 Native 即时响应+后续 GET 两份原件。

3.5 顺序与日期
repo comments ORDER BY createdAt ASC；service 映射 createdAt.toISOString 后再按 createdAt.localeCompare ASC。
没有 isPinned/keyConclusion 排序，没有 comment.id tie-break。相同 ISO 毫秒保持输入顺序；
DB createdAt 精度更细的顺序必须先保留，不能先截毫秒再用 id 排序。全部 SQL 排序键完全相同的
记录相对顺序没有完整合同；验收只能比较该等价组内容，不声明某次 Native 返回就是稳定 SSOT。
createdAt 是 datetime/timestamptz → JS Date → UTC ISO 毫秒，不是 date-only。
