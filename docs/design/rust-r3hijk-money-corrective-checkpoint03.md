# R3H–K 金额正确性补正

本记录延续用户的业务正确性准则及本批依赖纠偏，不改写联合 G1 或历史候选的验收原件。当前 G3 保持阻断，直到精确金额修复和定向复验完成。

非作者 C 指出成本累加及报价格式化经过 binary64 的风险；Root 在候选 `37ad04b20b699a8d9bafcaf3e0824f09fbe51e548108ee0ad3cf02ec232692af` 实测确认：`phase41` 合法金额 `9007199254740993.01` 经成本和报价 POST 均返回 201，但成本父合计、成本子项及报价金额均落成 `9007199254740994.00`。这是本轮发现的 `existing-baseline-drift`，按业务正确性构成 P2，不能用 Node 同样行为豁免。

修复限定既有技术成本与报价模块：使用已锁定十进制依赖进行金额解析、等式比较、合计和格式化，保留合法分位；实际 `numeric(18,2)` 金额及 `numeric(18,4)` 数量／单价边界在写入前校验，合计溢出返回明确 400。报价含税／不含税金额精确比较；调用者提交的 `grossMarginRate` 继续按既有 signed decimal 规则处理，不增加自动计算或重新定价规则。不改 Native、Angular、公开 DTO、生成客户端、依赖锁或 DDL，不新增交付操作数。

验收须覆盖大金额父子一致、报价读写、普通分位求和、边界合法值、溢出及等式错误无写入；修复后重新执行 Rust fmt/clippy/test/release、三版本域实际故障／并发及基础业务回归。四 UI cell、H/I/J/K 用例保留原候选绑定；只有明确不受成本／报价计算修改影响的证据才按文件因果边界复用，不宣称全部在新候选重跑。

保留 `phase39` 的单价 fixture 越界和 `phase40` 的枚举 fixture 误值，分别标记其工具前提错误；`phase40` 成本错误及合法 `phase41` 两接口错误仍为真实缺陷证据，不将失败改标通过。终态清理包含这些部分运行新增的项目、版本、会话及其他自有行。
