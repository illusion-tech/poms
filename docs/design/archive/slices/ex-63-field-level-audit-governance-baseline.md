# EX-63 字段级审计治理与首批范围需求精化

> 状态: G0 scope refined
> 日期: 2026-05-06
> 关联 tracker: EX-63, EX-63A, EX-63B, EX-63C, FE-57
> 前置: 统一运行时审计基础设施, EX-31/EX-32 Lead 主链, EX-61 销售情报, EX-62 客户联系人性别字段
> 后续实施: EX-63A Lead 基础信息字段审计, EX-63B CRM 销售事实字段审计扩展, EX-63C 实体级审计读取边界, FE-57 编辑历史前端入口

## 1. 背景

当前系统已经具备统一 `audit_log` / `security_event` 基础设施, 也在平台治理、附件、销售跟进替代 / 作废、线索评分覆盖等场景写入运行时审计。但线索基础信息、客户联系人、销售情报和部分核心业务对象的普通编辑仍主要依赖 `updatedBy / updatedAt / rowVersion`。

这只能说明“最后一次是谁更新的”, 不能回答:

- 谁在什么时候把某个字段从什么改成什么。
- 这次修改是否经过受控入口和乐观锁版本。
- 修改是否涉及个人信息、销售事实或转项目判断依据。
- 后续争议、复盘或主管检查时如何还原编辑过程。

因此需要补充字段级审计。字段级审计不是业务快照、不是状态历史、也不是安全事件。它的职责是记录受控编辑命令的字段变更证据。

## 2. 目标

EX-63 冻结字段级审计的治理原则和首批实施顺序, 不直接交付运行时代码。

本基线需要支持:

- 对关键可编辑业务对象形成可查询的字段变更历史。
- 区分业务历史、字段审计和安全事件, 避免互相替代。
- 对个人信息和敏感/准敏感字段做审计最小化与脱敏。
- 先覆盖当前用户可感知缺口最大的 Lead / CRM 编辑场景, 再扩展到项目和合同核心字段。
- 前端先做实体详情内的“编辑历史”只读入口, 不先做全局审计中心。

## 3. 三层留痕边界

| 类型     | 代表数据                                   | 回答的问题                         | 不承担的职责                     |
| -------- | ------------------------------------------ | ---------------------------------- | -------------------------------- |
| 业务历史 | 线索评分历史、附件版本、跟进替代链、状态链 | 业务事实如何演进                   | 不逐字段解释普通编辑 diff        |
| 字段审计 | `audit_log` 中的 `*.updated` 事件          | 谁在何时把哪些字段从什么改成什么   | 不替代业务状态机或审批流         |
| 安全事件 | 登录失败、权限拒绝、敏感字段脱敏/拒绝      | 谁尝试访问什么、为什么被阻断或脱敏 | 不记录正常业务字段编辑的全量事实 |

字段审计应复用统一 `audit_log`, 但不得把 `audit_log` 改造成通用事件溯源框架。业务对象的权威当前状态仍以主表和业务快照/历史表为准。

## 4. 首批范围

### 4.1 第一优先级: Lead 基础信息

原因: 当前已补齐前端编辑入口, 线索名称、来源、需求、预算、金额、紧迫度、预计决策日期会直接影响评分、闸口提示和销售判断。

首批字段:

| 字段                   | 审计要求            | 备注                           |
| ---------------------- | ------------------- | ------------------------------ |
| `leadName`             | 记录 before / after | 用户最容易感知的名称变更       |
| `sourceId`             | 记录 before / after | 建议记录 ID, 展示层再映射名    |
| `demandDescription`    | 记录摘要或脱敏值    | 长文本不宜全量写入审计日志     |
| `budgetStatus`         | 记录 before / after | 会影响评分和闸口解释           |
| `estimatedAmount`      | 记录 before / after | 金额属于业务敏感信息, 控制可见 |
| `urgency`              | 记录 before / after | 会影响评分                     |
| `expectedDecisionDate` | 记录 before / after | 日期语义必须保持 ISO date      |

### 4.2 第二优先级: CRM 销售事实

原因: 客户联系人、机会关系人、竞争态势和销售发现是销售主管关注的关键事实, 会影响推进判断和新人销售质量。

首批对象:

- `CustomerContact`: 姓名、联系方式、职务、性别、是否关键联系人、备注。
- `OpportunityStakeholder`: 角色、影响力、态度、决策链位置、关系说明。
- `CompetitorIntelligence`: 竞争对手、优势/劣势、竞争状态、应对策略。
- `SalesDiscoveryRecord`: 采购流程、预算来源、客户痛点、下一步对象、缺口补齐状态。

要求:

- 联系方式、备注、关系说明等个人信息或自由文本不应默认全量复制到审计日志。
- 审计日志至少能说明字段发生了变化, 必要时用脱敏值、摘要或 `changed: true` 表达。
- 禁止把婚姻、籍贯、私人偏好等私人画像扩展为评分或自动决策字段。

### 4.3 第三优先级: 项目与合同核心字段

原因: 项目和合同的金额、负责人、状态、关键日期和条款摘要会影响交付、回款、提成和责任界定。

后续对象:

- `Project` 核心可编辑字段。
- `Contract` 核心可编辑字段。
- 合同条款快照或经营快照中已经具备版本链的对象, 不重复做“字段审计替代业务快照”, 只补普通编辑命令的审计缺口。

## 5. 审计事件规范

### 5.1 事件命名

字段级审计事件使用动词过去式:

| 场景         | 事件类型                          | targetType 建议           |
| ------------ | --------------------------------- | ------------------------- |
| 线索基础编辑 | `lead.updated`                    | `lead`                    |
| 客户联系人   | `customer-contact.updated`        | `customer-contact`        |
| 机会关系人   | `opportunity-stakeholder.updated` | `opportunity-stakeholder` |
| 竞争态势     | `competitor-intelligence.updated` | `competitor-intelligence` |
| 销售发现     | `sales-discovery-record.updated`  | `sales-discovery-record`  |
| 项目核心编辑 | `project.updated`                 | `project`                 |
| 合同核心编辑 | `contract.updated`                | `contract`                |

平台治理已有 `platform.*` 事件, 附件已有 `attachment.*` 事件, 评分覆盖已有 `lead-score-override.*` 事件, 不在 EX-63 中重命名。

### 5.2 快照结构

`beforeSnapshot` / `afterSnapshot` 只记录发生变化的字段, 不复制整表。

推荐结构:

```json
{
  "leadName": "old value",
  "budgetStatus": "unknown"
}
```

`metadata` 推荐包含:

```json
{
  "changedFields": ["leadName", "budgetStatus"],
  "sourceCommand": "update-lead",
  "expectedVersion": 3,
  "redactedFields": ["demandDescription"],
  "businessContext": {
    "leadId": "..."
  }
}
```

### 5.3 个人信息与敏感信息处理

审计日志不能成为敏感信息副本。第一版规则:

| 字段类型           | 审计策略                                      |
| ------------------ | --------------------------------------------- |
| 枚举、日期、布尔值 | 可记录 before / after                         |
| 金额               | 可记录 before / after, 但读取端必须受权限控制 |
| 手机、邮箱、微信   | 默认脱敏, 如 `138****1234`                    |
| 长文本说明         | 默认记录摘要、长度变化或 `changed: true`      |
| 私人画像自由文本   | 不鼓励采集; 若已存在, 审计只记录 changed flag |
| 密码、Token、密钥  | 永不进入审计快照                              |

### 5.4 事务与失败处理

- 成功编辑的业务写入和 `audit_log` 写入应在同一事务内完成。
- 被业务规则拒绝但有审计价值的命令可以写 `result = rejected`。
- 系统异常失败不要求每次都写 `audit_log`; 技术错误归应用日志和监控处理。
- 无实际字段变化时不应写 `*.updated` 成功事件, 可以直接返回当前对象。

## 6. 读取与前端边界

当前已有 `GET /audit-logs`, 但它是平台级全局查询入口, 由平台管理权限保护, 不适合直接作为普通销售详情页的默认入口。

后续应拆出实体级审计读取边界:

- 销售/主管在拥有对象读权限时, 可以在对象详情内查看该对象的编辑历史。
- 平台管理员仍可通过全局审计接口做跨对象检索。
- 前端第一版只做 Lead / Customer / Project 详情页内只读历史, 不做全局审计中心、导出、图表或全文检索。

实体级读取可以通过扩展现有 audit query service 或新增 scoped query route 实现; 具体 route surface 必须在 EX-63C 的 G1 中冻结并同步 `api-route-canonical-inventory.md`。

## 8. 验收标准

EX-63 后续运行时切片必须满足:

1. 编辑命令只在字段真实变化时写入 `audit_log`。
2. 审计载荷包含 `eventType`、`targetType`、`targetId`、`operatorId`、`requestId`、`result`、`beforeSnapshot`、`afterSnapshot`、`metadata.changedFields`。
3. 个人信息、金额和长文本按字段策略最小化或脱敏。
4. 业务写入和审计写入具有一致性; 不允许业务成功但审计静默丢失。
5. 单元测试覆盖: 有变化写审计、无变化不写审计、敏感字段脱敏、并发版本冲突不写成功审计。
6. 前端只展示后端返回的审计事实, 不自行推断 before / after。

## 9. 当前结论

字段级审计应作为后续横切治理能力补齐, 但第一刀必须收敛到用户当前能感知和业务风险最高的 Lead / CRM 编辑场景。评分历史、附件版本、销售跟进替代链和状态历史继续保留各自业务语义, 不用字段级审计替代。
