## 项目状态、路径和 blocker

项目写前查 `findById(projectId)`；missing 抛 `NotFoundException("Project {projectId} not found")`。再拒绝 `project.status==='closed'` 或 `currentStage` 不在 `assessment/scope-confirmation/commercial-closure/contracting`。没有 owner/org/scope限制，没有要求 actor 是主责，没有再次要求 active customer、active operator、技术成本包、材料齐备或审批记录。`pending-approval/blocked/on-hold/completed` 等非closed status 在4个允许stage仍未被额外拒绝；不能套用项目基础修改的 active/blocked 限制。

`assertBidCommercialPathConsistent` 只有三项原规则，按以下次序抛400：

1. `bidMode=not-required` 时，必须同时 `decision=not-required` 与 `resultStatus=not-applicable`，否则 `not-required bidMode must use not-required decision and not-applicable resultStatus`；满足后return。
2. 其他 mode 的 `decision=not-required`：`not-required decision requires not-required bidMode`。
3. 其他 mode 的 `resultStatus=not-applicable`：`not-applicable resultStatus requires not-required bidMode`。

`decision=pending/no-bid`、`result=lost/cancelled` 和任何合法过程stage均允许形成版本。`blockerCount` 是材料中 `blocksNextStep=true && materialStatus不在ready/not-required` 的数量，加 decision pending/no-bid 的1，加 result lost/cancelled 的1。timeline、时间先后与 bidder mode 不额外计数。

## 版本、持久化与未知事务事实

service 按以下静态次序执行：项目读取→状态/stage校验→路径校验→读取current effective→将旧对象内存标记 `isCurrent=false/status=superseded/updatedBy=operator`→randomUUID新parent→建立children→`saveProjectBidCommercialProcess`→返回新parent。

- current query严格 `projectId + isCurrent=true + status=effective`，order `version DESC,effectiveAt DESC,createdAt DESC`；list只按projectId，保留所有状态与版本，用同一order。
- 新版本 `version=previous.version+1`，无current则1；`supersedesId=previous.id`或null；`status=effective/isCurrent=true`；`effectiveAt=new Date()`；createdBy/updatedBy=请求user.sub。不存在 `MAX(version)+1`、校验全部历史链或先重建current。
- 新children属于新parent；旧children不更新/删除。material与timeline id走原ORM UUID默认，parent由Node randomUUID生成。表没有 materialKey/eventKey/sortOrder唯一约束。
- repository将 `[currentProcess,...materialItems,...timelineItems]`，再append旧parent，以同一EntityManager `persist(entities).flush()`。本方法无显式transaction/lock/retry；service也无显式transaction。
- entity `.version()` 的 `rowVersion` 默认1；旧parent脏更新由ORM处理其乐观版本。新请求没有 expectedVersion。不得把原ORM冲突误改为新409业务协议。
- schema已有 `(project_id,version)` unique和 `project_id where is_current=true` partial unique。current predicate排除 `status!=effective`，partial unique不排除这种行；不能将二者混为一谈。
- project FK restrict；supersedes self-FK set null；children parent FK cascade。process字段为varchar/text/integer/timestamptz，枚举仅TS类型，无本片新增DB CHECK。`tender_no/bid_package_no`来自后续 EX-35a migration，不能只执行EX-27视为完整schema。
- current缺失但历史version1仍存在时，源码仍尝试version1；不得擅自按历史max修复。未知current/status组合也不得静默修复。

**Root必须先Native见证的事实**：正常第二版本是否成功、ORM insert/update排序和partial unique冲突、managed旧版rowVersion CAS、auto-flush点、隐式flush事务边界、session managed flush的相对次序、并发首建/替换/第三方旧行更新、唯一冲突的原HTTP状态/body、任一child/旧版更新/session触发故障后的全部rollback与残留。单测mock `save...=resolved` 不是这些事实的证明。先采原Native SQL/HTTP/持久化快照，再决定Rust语句次序与事务；不得以“合理的原子性”增强或修复原Native。

## 认证、CSRF、敏感字段和审计

原全局guard注册顺序：SessionAuthGuard→AuthCsrfGuard→PermissionsGuard→DTO pipe→controller。session resolve检查active user并touch会话；POST CSRF失败在权限检查之前记录`auth.csrf.failed`，权限不足记录`authz.permission.denied`；有效session缺失等错误按公共来源处理。非法JSON/路径层解码与guard先后由Root真实HTTP裁决。
