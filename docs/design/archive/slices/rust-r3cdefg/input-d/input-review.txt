## 2. 共同 DTO、标量和错误边界

1. Nest 全局 `ZodValidationPipe` 调用原 schema `parse`；`z.object` 对未知键进行 strip。本片不添加 `.strict`，不自动把陌生键当合法更新字段。
2. 默认错误对象来自 `ZodValidationException`：`{statusCode:400,message:'Validation failed',errors:issues}`；若原 parse 抛出的异常没有 issues，`errors` 会被 JSON 省略。没有额外 `error` 字段。字段 issue 顺序、path、code、pattern、message、同字段多条 issue 和 refine 是否执行由原 schema oracle / HTTP witness 冻结。
3. 字符串没有全局 coercion；数字、布尔、数组、对象、null 与缺失需分别比较。JS 对异常 `.length` 对象 / 数组的 Zod 路径不能由通常标量校验猜测。
4. 原 R3A/B 联合基线已记录锁定 Zod 4.6.1 的字符串 trim 后 min/max 按 Unicode code point 实测。此记录作为本批共同裁决的输入，Root 仍应对本片受影响 schema 复验边界。它不改变业务源码显式使用 JS UTF-16 `text.length` / `slice` 的审计长度和 Todo 截断。
5. trim 是原 JS 空白集合；须覆盖 ASCII、NBSP、BOM、Unicode 分隔空白、零宽空格差异、emoji、组合字符、未配对 high/low surrogate 和 JSON 转义。Rust `str::trim`、UTF-8 字节数或无条件替换字符都不能代替原规则。
6. `z.uuid()`：不 trim，接收版本 1–8 与合法 variant，也包含 nil UUID 与全小写 max UUID 的原 pattern。大小写、nil/max、坏 variant、version 0/9、无连字符、前后空白以及 URL/query 重复键要由原 DTO 断言。传入 service 的 UUID 原拼写与 DB canonical 化可能影响 JS 严格相等，不能提前统一小写后再比较。
7. path ID 没有 DTO UUID 校验。坏 path UUID 的真实 PG/ORM/HTTP错误、大小写/连字符/特殊转义等须先 Native witness；不能新增 400 UUID pipe，也不能默认把其变成 404。
8. 日期为 `z.iso.datetime()`，非仅日期，不启用 offset/local 选项。Root 冻结 Z、秒/小数、闰日、offset、缺失时区、无效日历、扩展年、过长小数、负/未来时间和 ISO 归一化。服务不要求 `nextFollowUpAt >= occurredAt`，也不要求 occurredAt 非未来。
9. 普通 Native `BadRequestException` / `NotFoundException` / `ConflictException` 用默认 Nest string exception envelope；数据库/ORM失败用原未知错误路径。Root 共享错误桥裁决前作者不得自行发明映射。
10. 认证、CSRF、permission guard、请求 ID 与 managed session 的 pending flush 属 Root 公共接线；对七操作逐项覆盖无会话、Cookie、Bearer、缺权限、any/all差异、写CSRF失败、允许的四认证组合。此处不增加 owner / organization / scope 权限判断。

## 4. R3F：字段、锚点与 owner 解析

源：shared-contracts.ts 2396–2402、3460–3615；sales-follow-up controller 15–94、service 26–367、repository 14–307、mapper 18–51、entity 20–171；CustomerService.requireActiveCustomer 258–264；DictionaryService.requireActiveItem 66–76。

### 请求与查询

- GET：customerId/leadId/projectId 均 optional `z.uuid()`，不可 null；lifecycleScope optional enum `active/all`。至少一个 anchor，错误 `At least one anchor is required for sales follow-up query`。未传 scope 默认为 active；没有客户/线索/项目存在性查询。
- filter 是 `(customer_id = customerId 如有) AND (lead_id=leadId OR project_id=projectId 如有)`；两个机会锚点不是 AND。scope active 加 status active，all 不加状态条件。排序 `occurred_at DESC, created_at DESC`，没有额外 tie-break；返回数组。
- POST create：customerId required；leadId/projectId optional nullable UUID，可同时存在；不强制二选一，不验证 project.sourceLeadId 等于 leadId。
- create/replace：followUpType required DictionaryCode，trim、1..64、`^[a-z][a-z0-9-]*$`；occurredAt required ISO datetime；summary required trim 1..2000；detail optional nullable trim 1..8000；outcome required enum `progress/waiting-customer/risk-discovered/deferred/close-recommended/no-response/other`；nextFollowUpAt optional nullable ISO datetime；ownerUserId/ownerOrgId optional nullable UUID。
- replace 另外 required replacementReason trim1..1000，expectedVersion required number/int/positive；customerId/leadId/projectId/status/links/rowVersion等未知键 strip，不更换旧记录锚点。
- void：reason required trim1..1000，comment optional nullable trim max1000（空串允许），expectedVersion required number/int/positive。无字符串转数字。正小数/0/负数/NaN不可JSON等按原DTO错误形状比较。

followUpType DTO允许64字符，但 entity / DDL列为varchar32；字典表允许64字符。本片不能缩窄DTO或继续使用原始6值硬编码。当前 EX58C migration 已移除 chk_sales_follow_up_type；Root须覆盖真实active自定义字典值、inactive、missing，以及33..64合法字典值的DB错误。

### create 校验与 owner

执行先后：操作人存在性 → requireActiveCustomer → 可选lead → 可选project → resolveOwner → requireActiveItem(sales-follow-up-type) → 构造record → saveWithReminderSync → mapper。

操作人缺失404 `Platform user <id> not found`；客户缺失404 `Customer <id> not found`；客户非active400 `Customer <id> is not active`。lead/project只要求存在、customerId严格相等，没有状态或owner/scope验证；不同客户400 `Lead/Project <id> does not belong to customer <customerId>`；缺失404 `Lead/Project <id> not found`。两锚点同客户即可，不要求两者互相关联。

create owner规则：

1. defaultOwnerUserId=`project.ownerUserId ?? lead.ownerUserId ?? operator.id`。
2. defaultOwnerOrgId=`project.ownerOrgId ?? lead.ownerOrgId ?? operator.primaryOrgUnitId ?? null`。
3. ownerUserId缺失采用默认，显式null清空；非null存在性查询，缺失404 `Platform user <id> not found`。不校验active、组织成员关系、数据scope或操作者等于owner。
4. ownerOrgId缺失采用 `ownerUser.primaryOrgUnitId ?? defaultOwnerOrgId`；显式null清空。非null存在性查询，缺失404 `Org unit <id> not found`。即使owner显式null，org仍可由锚点/操作人默认；即使owner变化，原上下文org仍可作为fallback。
5. ownerUser/Org在查询后用返回entity.id，保留原操作人identity map规则的 Root 统一裁决。

构造active记录；summary trim，detail trim或null；next空值变null；createdBy/updatedBy=operator.id；created时无success审计。发生时间与下一次时间没有先后/未来限制。

### replace / void 的差异

两者先requireOperator、按path读旧record，缺失404 `SalesFollowUpRecord <id> not found`；再比较expectedVersion；不匹配409 `sales-follow-up-record version <expected> does not match current version <current>`；再判断status active。只有active可以替换或作废；400消息分别为 `Only active sales follow-up records can be replaced/voided, current status: <status>`。先版本后状态，组合错误优先级必须保持。service有缺expectedVersion的400支路，但真实HTTP先被required DTO拒绝，不能用service测试替代HTTP断言。

loadRecordAnchors只要求customer存在，不再requireActiveCustomer；对旧lead/project继续检查存在和同客户。不新增closed/inactive限制。

replace ownerUserId缺失保留currentRecord.ownerUserId；null清空；提供则查用户。ownerOrg缺失fallback按顺序：`ownerUser.primaryOrgUnitId ?? (ownerUserId缺失 ? currentRecord.ownerOrgId : null) ?? project.ownerOrgId ?? lead.ownerOrgId ?? operator.primaryOrgUnitId ?? null`；显式org null清空；非null查存在。只提供ownerOrg时也会重新查询ownerUser，用户当前primaryOrg可能优先于旧org。

replace再验证字典，分配新UUID，捕获beforeSnapshot，然后将旧记录status=superseded/replacedByRecordId=newId/updatedBy=operator；新记录复制customer/lead/project锚点，使用替换body重建业务字段，status=active/supersedesRecordId=oldId/replacementReason trim，createdBy/updatedBy=operator。detail与next省略变null，并非保留旧值；owner按上述独立规则保留。新rowVersion默认1；旧rowVersion随真实flush增加，精确版本/时间按witness。返回新记录。

void不查字典、不重新解析owner，只查现有owner user/org（找不到则mapper名字null）；设置status=voided、voidedAt=now、voidedBy=operator.id、voidReason=`trim(reason)`加非空trim(comment)的`: `后缀、updatedBy=operator。reason+comment组合可超过单字段1000，无新增组合限制。返回原记录的作废态。

### follow-up 审计和 mapper

replace保存/提醒sync完成以后另调用recordAudit：eventType=`sales-follow-up.replaced`、targetId=旧ID；metadata replacementId/replacementReason/before/after。void同样保存以后另记eventType=`sales-follow-up.voided`、targetId=原ID；metadata reason/before/after。targetType均sales-follow-up-record；requestId或null；result success。没有向recordAuditLog传业务EM。

## 6. 数据库、并发、故障与共享接线要求

累计迁移保持92份原始字节。关键DDL：EX44建follow-up；EX48A加active/superseded/voided、双向self FK及非nullsupersedes/replacedBy独立唯一索引；EX58B稳定小写Todo枚举；EX58C移除follow-up固定type CHECK并引入字典；EX61建contact；EX62加gender。contact.customer / follow-up.customer/lead/project FK restrict；follow-up.owner user/org FK set null；createdBy/updatedBy/voidedBy是nullable UUID而非新加FK。

follow-up保存与reminder查询可能auto-flush；查询前的managed业务记录、old/new互指、reminder清理、默认时间、rowVersion、session写入、审计独立flush必须用Native真实SQL观察。至少在record insert/update、stream SELECT、todo update/insert、cancel SELECT、业务最后flush、audit insert等阶段注入受控失败。每次检查HTTP、业务行、Todo行、audit、session、版本，结果可能是已部分提交；Pending不能写成rollback通过。

并发覆盖contact同一行不同/相同字段、follow-up双replace、replace-vs-void、双void、同stream多create、不同stream隔离、同source open唯一冲突、dictionary停用、锚点/owner变化及会话CAS。真正Native冲突码/错误body/获胜者数量/新旧链/Todo终态/审计数量由Root先冻结；不把CAS loser统一改409，亦不为没有API版本要求的操作新增expectedVersion。
