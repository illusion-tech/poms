## 3. Zod、缺省、null、文本、ID、日期与数字

### 3.1 共同规则

- `z.object` 未用 strict/passthrough；顶层及每个子对象未知 key strip。字段解析/错误顺序按 schema 声明顺序；nested errors 路径含原数组索引。必须保留 `Validation failed`、errors 数组、type/format/enum/length issue 形状，Root 用 Native 输出冻结，不只比 HTTP 400。
- JSON 无 undefined 字面量；“undefined”对应属性缺失。required 不接受缺失/null；`.optional()` 只允许缺失；`.nullable().optional()` 接受缺失或 null；数组 `.default([])` 仅对缺失生效，null 失败。没有 string/number/boolean 自动 coerce。
- 所有下列文本、数字字符串 `.trim()` 使用 ECMAScript trim；非空和 max 在 trim 后执行。枚举、UUID、dueAt 不 trim。保持原大小写、Unicode、内部空白、换行；不做 NFC 或全角数字转换。
- Unicode 边界需 Root 原依赖实测：astral（BMP 最大长度边界旁）、组合字、NBSP/BOM/U+0085/U+200B、孤立 surrogate、NUL。现 Rust `JsString`/Wire 支持原 UTF-16；不可用 serde 的有损字符串提前吞掉 Native 可返回的孤立 surrogate。Node pg DB 边界替换与 POST immediate / GET reread 差异属于待见证项。
- ID body 使用 `z.uuid()`：不 trim；大小写文本须保留到 JS 严格比较；UUID v1-v8、nil/max、variant 错误的精确接受面交 Root Native。现 Rust public scalar/验证实现可参考，但不是本次实测。
- route ID 由 PG UUID 类型查找，body reference ID 后续与 current.id 做 `!==`，大小写字符串即使同一个 UUID 也可能拒绝，必须实测并保持。无业务编号字段、无业务编号生成，不借用 R3A/B 编号机制。
- `sortOrder` 是 `z.number().int().nonnegative().optional()`：不接数字字符串；缺失服务按原数组 `index + 1`，0 有效，允许相同排序号；不因 PG int4 范围或唯一性增强 DTO。超 JS safe integer/.int() 边界与 int4 overflow 分别观察。
- 数字字符串模式均 ASCII digit：money `/^\d+(\.\d{1,2})?$/`；quantity/unitPrice `/^\d+(\.\d{1,4})?$/`；taxRate `/^\d+(\.\d{1,8})?$/`；grossMarginRate `/^-?\d+(\.\d{1,8})?$/`。允许 0、leading zeros；拒 `+1 / -1`（gross 可负）、`.1 / 1. / 1e2 / 全角数字`；整数部分无长度上限，不在 DTO 额外限 numeric precision。
- condition `dueAt` 是 `z.iso.datetime().nullable().optional()`；服务 truthy 时 `new Date(...)`，否则 null，mapper `.toISOString()`。默认 UTC Z/seconds、任意 fractional、闰日/0000年、长fraction截毫秒、offset和小写拒绝、PG year0交 Root 原依赖见证；不能改成日期 date-only。

## 4. 成本命令与金额实际算法

`project.service.ts:650-765,852-881,914-921` 的顺序必须保留：

1. find project → 404 → stage/status 400。
2. 按 costItems 原顺序：currency 必须与 package 完全相等（trim后的大小写仍敏感），否则 `costItems[${index}].currencyCode must equal package currencyCode ${currency}`；随后各项转 Number，拒非有限或负值，比较 `Math.abs(including - (excluding + tax)) > 0.0001`。
3. find current package（projectId、isCurrent true、status effective；version/effectiveAt/createdAt DESC）；若有先改旧对象 `isCurrent=false,status=superseded,updatedBy=operator`，尚未显式 flush。
4. 三列分别用 JS number 从0按输入数组顺序 reduce；各自 `.toFixed(2)` 变总额字符串。每项三金额也各 `Number(...).toFixed(2)`；quantity / unitPrice 不做 Number 运算，原字符串交 ORM decimal。
5. highestRiskLevel 为全部 risk 最大 R1<R2<R3<R4（含closed，空=null）；blockerCount=`blocksNextStage && riskStatus !== closed` 条数 + `allowNextStage ? 0 : 1`。tax pending 不计数；accepted但blocks=true仍阻断。
6. 新随机 UUID，version=旧version+1或1，isCurrent=true,status=effective,supersedesId=旧id或null；effectiveAt取一次new Date，createdBy/updatedBy=operator，createdAt/updatedAt/rowVersion由entity onCreate/version机制。三组子项不显式传id，entity/DB默认`gen_random_uuid()`生成，packageId显式传入，sortOrder缺省index+1。
7. persist `[new package,...scope,...risk,...cost,old?]`.flush；不手动更新 project，不写编号/审批/业务audit。

金额实现要点：Binary64 + JS Number + JS toFixed，而不是定点加法。现有 public `compat::scalars::{legacy_number,js_to_fixed}` 可复用。不能用 SQL SUM 或每项先round再sum。Root 要见证 >2^53 近旁、numeric(18,2)最大边界、巨长数字Infinity、leading-zero和0.10+0.20、多项顺序对总额的影响，以及POST立即返回/PG numeric/GET字符串补零。DTO允许的超precision合法文本交数据库时，错误是Native实际500/约束失败面，不另改400。

## 5. 报价命令、真实生产者与引用规则

`project.service.ts:557-647,793-849` 顺序：

1. project 404及stage/status400。
2. 读取真实当前成本：`projectId + isCurrent=true + status=effective`；无或current.id与输入字符串严格不等，400 `technicalCostPackageId must match the current effective technical cost package`。不额外要求成本allowNextStage、taxReviewed、blockerCount=0、technical feasible。成本币种不等，400 `currencyCode must equal technical cost package currencyCode ${currency}`。
3. 读取真实当前竞标，随后执行以下原规则；不调用报价前置workspace blockers作为命令验证。
4. 报价金额 Number finite/nonnegative、taxRate同样检查、`inclusive+0.0001 < exclusive` 时400；非null grossMarginRate只要求Number finite。只对两报价 `.toFixed(2)`，taxRate/grossMarginRate保持原字符串到decimal ORM；不重算毛利或税额。
5. 查旧current review后在内存置superseded；新UUID/version/supersedes。blockerCount=condition `requiredForContracting && status===open`条数 + decision在pending/rejected/escalation-required时1；readyForContracting=decision为released/conditional-release且blockerCount=0。条件closed或waived不阻断，默认required=false；独立记录ownerRole及全部引用，不变更project。
6. persist `[new review,...conditions,old?]`.flush。effectiveAt new Date，entity自动时间/version；condition dueAt new Date后持久化。

| 分支 | Native 实际要求 | 必须保持的开放面 |
| --- | --- | --- |
| bid | bidCommercialProcessId truthy；等于该project当前effective process.id；resultStatus不为lost/cancelled/not-applicable | 不验证bidMode、decision、blockerCount；no-bid + pending result不自动拒绝；无合格process时400 |
| direct-commercial且有bid ID | ID等于当前process；bidMode是direct-commercial/not-required | 未检resultStatus、decision、blockerCount；lost/cancelled/not-applicable可被该分支接受 |
| direct-commercial且无bid ID（missing/null） | 不检查竞标引用 | 即使当前process为公开招标/no-bid/lost等仍可无引用创建；不强制生成not-required process |
| released/conditional-release/escalation-required | 六个truthy引用同时存在：commercialReleaseBaselineId、approvalScenarioKey、summaryPackageKey、summarySnapshotId、projectionLevel、exportPolicy | 不查询baseline或summary业务归属/状态/场景一致性；两个UUID只靠既有FK存在性 |

| pending | 不额外要求六引用 | 允许部分引用；存在的UUID仍受PG FK约束 |

真实集成必须由成本Rust POST产出current.id，再由竞标Rust POST产出current.id，报价Rust POST消费二者；包括成本V2后旧ID拒绝、竞标V2后旧ID拒绝；已存在报价workspace继续按review保存的旧cost/bid ID读取历史，而非悄悄换成最新版本。无需迁移R4写链/创建商业baseline或summary本体来宣称本片完成；Root可以调用已交付机制或受控fixture准备外部FK，但要明确不等同本片交付其写链。

### 6.1 原提示优先级（不得“优化”）

- C空：reason `尚未形成技术与成本测算版本包。`；next `补齐技术可行性、范围边界、风险项和成本税务估算。`。
- C当前reason顺序：不allow→`技术与成本版本包尚未允许进入下一阶段。`；每个阻断且非closed风险→`${riskCategory}：${riskDescription}`；tax pending→`税务成本假设仍待复核。`。
- C next先判断allow=true且风险全部不阻断或closed→`进入商务收口前，保持当前版本包作为报价和签约前判断依据。`，即使tax pending也优先此句；否则tax pending→`先完成税务成本复核，再判断是否进入商务收口。`；否则→`先关闭阻塞风险或更新版本包，再进入商务收口。`。blockerCount、reasons.length、next不是统一重算同一个条件。
- G空前置reason顺序：无成本→`尚未形成可引用的技术与成本版本包。`；有成本且!allow→`当前技术与成本版本包尚未允许进入报价评审。`；tax pending→`当前技术与成本版本包的税务成本仍待复核。`；当前bid结果lost/cancelled→`当前竞标 / 商务过程结果不能直接支撑报价评审。`。若全空用`尚未形成报价与毛利评审记录。`。前置reason非空next=`先补齐技术成本、税务复核或商务路径依据，再发起报价与毛利评审。`；否则`基于当前技术成本和商务路径，形成报价、税务条件、回款条件与毛利评审结论。`。无bid本身不形成reason。
- G有review reason顺序：引用cost缺失→`报价评审引用的技术与成本版本包已不可用。`；pending→`报价与毛利评审尚未形成放行结论。`；rejected→`报价与毛利评审已被否决，需要回到技术、成本或商务条件重新收口。`；escalation→`当前报价与毛利评审需要升级审批，暂不能进入签约就绪。`；每required且open条件→`${label}：${conditionSummary}`。不因旧cost被替代、taxPending、bid无效追加reason。
- G有review next：reasons非空→`先处理报价结论、升级审批或条件放行阻断，再进入签约就绪。`；否则ready→`可以将当前商业放行基线和摘要快照带入签约就绪。`；否则→`确认商业放行基线、审批摘要和签约承接关系后再进入签约就绪。`。

## 7. 持久化、失败与并发：静态已知 / 待 Native

- 成本四表：`project_technical_cost_package / project_technical_scope_item / project_technical_risk_item / project_technical_cost_item`。报价两表：`project_pricing_margin_review / project_pricing_margin_condition_item`。不加 migration、不改原DDL。
- 两主表 projectId FK restrict；supersedesId自FK set null；唯一(projectId,version)，partial unique(projectId) WHERE is_current=true（不含status谓词）；rowVersion default1 + ORM `.version()`。子表父FK cascade；子表无rowVersion/审计时间。
- 所有money numeric(18,2)，quantity/unitPrice numeric(18,4)，taxRate/grossMarginRate numeric(18,8)；主表有效/创建/更新时间及condition dueAt均timestamptz。
- review cost FK restrict、bid FK set null、baseline FK restrict、snapshot FK restrict。baseline/snapshot没有同项目复合FK。createdBy/updatedBy只是nullable UUID，不新加平台user FK。
- 未发现给本六表追加enum CHECK的后续迁移；遵守原已存在constraints，不创建新CHECK或业务检查。SQL numeric/int/text/UUID错误仍走原错误协议。
- Native service没有显式transaction、FOR UPDATE、expectedVersion入参或错误捕获。ORM flush可能用version predicate，可能把旧current UPDATE先于INSERT。仅凭`.version()`或unique不能断言实际CAS、锁模式、失败HTTP或“每并发必定一成功一409”。
- Root必须先Native见证：首版并发、已有current并发、旧rowVersion被外部更新、旧current读后被替换/删除、子表insert失败、numeric/FK失败、提交前断连；观察status/rawbody、行数/链/current/status/rowVersion、全部子表、session managed flush、审计安全事件和连接/事务终态。
- 原auth会话touch先独立SQL更新后把managed session字段写回；这些pending变化是否在本六读查询前auto-flush、写最终flush并入事务、预检查失败时发生以及flush失败回滚顺序，须分别见证。不要简单复制别域事务模型。
- 本命令在改旧current后没有显式repository查询，随后只有同步组装与flush；但session/ORM自动flush不因此可忽略。读取workspace中的Promise.all也不应静态宣称事务snapshot一致。
